# Material sources

These `.dsm` / `.dsf` files are the source for the materials under `Content/Materials`. The
`.uasset` files are build output and are committed alongside them, so **DreamGUI has no dependency
on DreamShader**: without it installed the materials are ordinary `UMaterial` and
`UMaterialFunction` assets and everything works. DreamShader is only needed to rebuild them from
text.

## Rebuilding

With [DreamShader](https://github.com/TypeDreamMoon/DreamShader) installed, `Plugins/DreamGUI/DShader`
is picked up automatically as a source root (*Project Settings ▸ DreamShader ▸ Scan Plugin Source
Directories*, on by default). Build one file at a time, functions before the materials that call
them:

```bash
powershell Plugins/DreamShader/.skill/dsc.ps1 compile <absolute path to the .dsf or .dsm> -Force
```

Do not use `-All`: it builds every DreamShader source in the project, not just this plugin's.

## Things that will bite

**`Backend = "Graph"` is pinned in every `.dsm` and must stay.** The project default is
`ThinCustom`, whose output is a `UDreamShaderMaterialInstance` — a class DreamShader owns. The
DreamGUI runtime module loads at `PostConfigInit`, before DreamShader, so a material built that way
fails to load at startup and anyone without DreamShader gets nothing at all.

**A plugin source root is read-only to the editor.** *Adopt Into Source* and VirtualFunction sync
only ever write the project's own source directory, so these files change by hand and by nothing
else. That is the intended arrangement: the text is the authoring surface, and an edit made to the
generated asset is meant to be rejected rather than absorbed.

**`sRGBToLinear` and the other engine HLSL helpers need a `Function` with an `#include`.** A bare
`UE.Expression(Class="Custom", …)` cannot carry `IncludeFilePaths` — it is an array property, which
DreamShader rejects as a literal — so a Custom node written that way compiles against a function
nothing declares. It fails only in the vertex-shader permutations, which is why it looks fine until
something asserts. `MF_DreamUI_Clip`, `MF_DreamUI_ConvertVertexColor`, `MF_DreamUI_RectBlock` and
`MF_DreamWidgetProperty` are written the correct way and are worth copying from.

**`GizmoMaterial.dsm` and `UnderlayAndOutline.dsm` do not build.** Their assets are hand-authored and
carry no DreamShader provenance, so a build refuses rather than overwrite them
(`already exists and was not generated by DreamShader`). The sources are kept because they are an
accurate decompilation and the obvious starting point for taking those two over deliberately.
