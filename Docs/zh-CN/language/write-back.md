设计器是这个文件的一个前端：在设计器里做的改动，就是对文本的改动。值写进装着它的那一行——或者在节点已有的行后面新加一行——
文件其余部分逐字节保持原样。设计器本身的用法见[设计器](../tools/designer.md)。

<a id="写什么不写什么"></a>

## 写什么、不写什么

写回比较的是**值**，不是源文本。对每一个可能改过的属性，它问的是：**按现在的文本重建，会不会得到树上现在的这个值？**
会，就说明文件已经这么写了，不管拼法如何都不写。所以：

- 在设计器里打开一个手写的文件，什么也不会被写。你写的 `(400,240)` 不会被改成 `(400, 240)`，`0.50` 也不会变成 `0.5`。
- 比较用的基准树是用编译器用的同一个建树器、从当前文本建出来的，所以样式、类默认值、枚举的拼法、本地化，答案都和真正编译时一致。
- 一个值来自样式的属性被改了，写成**节点上**的覆盖，而不会悄悄改动其他节点也在穿的样式。
- 没有 `.dui` 写法的值——对象引用、没有短写形式的结构体——直接跳过，不去猜。往作者的文件里写一个看似合理的错值，比少一个功能更糟。
- 一次刷新是一步撤销。什么都没变时根本不写：空的撤销步骤会让 Ctrl+Z 看似无效，用户再按一次就丢了前一步。
- 文本解析不了或建不了树时什么也不写：没有基准，每个属性看起来都变了，一次刷新就会在作者修错的途中把整个文件重写一遍。

写出来的格式和 VS Code 扩展的格式化一致（`=` 和箭头两边各一个空格、`}` 独占一行等），两者不会互相打架。

改动落在装着值的那一行上，不管节点的类型是怎么写的（容器类型、别名、无名节点都一样）；节点有 `@slot { … }` 块时写进那个块里；
无名节点按为它造的 id 定位。嵌套的组件实例里面的内容属于另一个文件，这里不写；`for` 在运行时造的副本不是任何一行，也不写。

文件在磁盘上被别人改了（比如在 VS Code 里保存），由此触发的重新编译以**文件**为准，不会把设计器里较旧的值刷回去。
设计器有一个待写的改动、而文件在它底下变了，这次什么也不写（[DUI7002](../diagnostics/codes.md#dui7002)）。

<a id="结构上的改动"></a>

## 结构上的改动

在设计器里加的 widget，按这个文件会用的类型写出来：这个类在本文件里有 `use … as` 别名就用别名，排布子节点的普通 widget 写成容器类型
（`VerticalBox Column`）。

拖进组件实例某个具名槽位的 widget，写进那个槽位的填充块 `slot Detail { … }`；实例还没有这个块时先写出它。

给一个无名节点改名，会把它的第一个 id 写在类型后面。改名前：

```dui
Widget Root {
    + HorizontalBox { Spacing = 14 }
    Text { Text = "Status" }
}
```

在设计器里把那个 `Text` 改名为 `Status` 之后：

```dui
Widget Root {
    + HorizontalBox { Spacing = 14 }
    Text Status { Text = "Status" }
}
```

给一个有名字的节点改名，会写上 `(was: OldId)`，让下一次编译把图表引用、绑定和动画轨道搬过去（见[节点与值](nodes-and-values.md)）。
`for` 或 `each` 的模板不会被删掉或移出循环：没有东西可重复的循环建不起来。

<a id="fill-简写"></a>

## `@fill` 简写

新的权重替换 `@fill 2` 里的数字；一个裸的 `@fill` 被改成别的规则时，变成 `@slot SizeRule = …`。改之前：

```dui
Widget Root {
    + HorizontalBox { }
    Text Label {
        Text = "Volume"
        @fill
    }
}
```

在设计器里把 `Label` 的 `SizeRule` 改成 Auto 之后：

```dui
Widget Root {
    + HorizontalBox { }
    Text Label {
        Text = "Volume"
        @slot SizeRule = Auto
    }
}
```

<a id="设计器拒绝写的改动"></a>

## 设计器拒绝写的改动

有几种东西没有一行可以写进去，设计器会说出来（[DUI7004](../diagnostics/codes.md#dui7004)），而不是凭空造一行：

- **由 `if` 显示或隐藏的 widget 的可见性。** 改条件，或者把 widget 移出分支。见 [if 与 for](control-flow.md)。
- **`@fill 2` 上 Fill 以外的 `SizeRule`。** 把它换成 `@slot SizeRule = …` 和 `@slot FillWeight = 2` 两行。
- **`rows` 表格里一行上的改动，除了某一列的值和这一行自己的块里的行。** 行的那一行只写得下它的列。列的值会被替换在它的格子里；
  但不能从设计器删除、移动、命名一行或给它加 `+` 块，也不能在表格旁边放节点（那个位置在表格里面）——这些去改文本。
  见 [rows 表格](rows.md)。

来自样式 `+ Component` 行的值也不写（[DUI7005](../diagnostics/codes.md#dui7005)）：样式是共用的，节点自己又没有 `+` 行装这个改动。
在节点上加一行（`+ VerticalBox { Spacing = 20 }`），或者去改样式：

```dui
style Column {
    + VerticalBox { Spacing = 8 }
}

Widget Root {
    + HorizontalBox { }
    Widget Left : Column {
        + VerticalBox { Spacing = 20 }
    }
}
```

<a id="写回的诊断"></a>

## 写回的诊断

| 代码 | 情况 | 怎么办 |
| --- | --- | --- |
| [DUI7001](../diagnostics/codes.md#dui7001) | 改动在文件里没有落点：不认识的节点、被绑定的属性、没有块的槽位 | 被绑定的属性由绑定决定，改绑定；其余在文本里补上落点 |
| [DUI7002](../diagnostics/codes.md#dui7002) | 待写的改动期间文件变了，什么也没写 | 等设计器按新文本刷新后再改一次 |
| [DUI7003](../diagnostics/codes.md#dui7003) | 语言写不出的值（非有限数），那一行保持不动 | 换一个有限的值 |
| [DUI7004](../diagnostics/codes.md#dui7004) | 改动的东西没有哪一行写着：`if` 决定的可见性、写不下改动的简写、表格行 | 照上文改文本 |
| [DUI7005](../diagnostics/codes.md#dui7005) | 改动的是样式 `+` 行给节点的值 | 在节点上加那一行，或改样式 |

<a id="向另一边走的那条缝"></a>

## 向另一边走的那条缝

把设计器的编辑**翻译成一行行 `.dui`** 的是 **`FDreamUITextWriteBack`**。它贯穿一条总规则：**比较值，绝不比较源文本**。

`FDreamUITextPatcher` 编辑的是**文本切片**；把设计器可能碰过的每个属性都交出去，会重写**值根本没变**的行 —— 作者写 `(400,240)`、打印器把同一个值拼成 `(400, 240)`，这行就被替换了。所以一次 flush 问的不是「哪里不一样」，而是：**「从当前文本重建，会不会产出树现在持有的那个值？」** 基线不是在这里解析的，而是**用编译器同一个 `FDreamUITextBuilder` 从当前文本建的整棵第二棵树**。

两条落地细节：**一次 flush 就是一条撤销步，否则什么都没有**（什么都没变时就没有 `SetContent` —— 空事务比没有事务更糟）；以及 undo **只做标记**、重建排到**下一 tick**（`FTransaction::Apply` 是**循环内部**广播的，同一事务里那些控件可能还没恢复）。

<a id="文本住在哪udreamuidocument"></a>

## 文本住在哪：`UDreamUIDocument`

在 `.dui` 方向下，**文本是唯一的真相**，设计器是它的图形前端。持有这一段文本的是一个 `UCLASS(Transient)` 的 `UObject`：**`UDreamUIDocument`**（在 `DreamGUIEditor` 里）—— 它只做一件事：**持有某一个 `.dui` 文件的全部文本**，好让 UE 的事务系统能撤销它。

**为什么必须是 `UObject`**：UE 的 undo 恢复的是**对象**。文本若留在事务之外，Ctrl+Z 把控件放回去了、文件那行还写着新值，下一次重新生成（重编译、重开、下一次无关的编辑）又把改动带回来 —— **撤销看起来生效了，然后静默地把自己撤掉**。

三条契约：

1. **调用方拥有事务。** `SetContent` 只调 `Modify()`，**从不自己开一个**；没有事务可加入时它会**大声抱怨**，而不是安静地产出一次不可撤销的编辑。
2. **内存是真相，磁盘是一个可能滞后的投影。** 一次失败的写（只读文件、没签出）**保留**这次编辑、如实报告，并在下一次 flush 时**重试**。
3. **`FlushToDisk` 从不擅自清只读位** —— 在版本控制的工程里只读 =「没签出」，一个偷偷把文件变可写的文本编辑器产生的合并，是**没人有 changelist** 的那种。

**一个文件一份文档，不是每个编辑器一份**：两个工具包同时打开一个 `.dui`、各持一份文档，就是两份 `Content`、两个磁盘哈希 —— A 的 undo 写了文件，B 的 watcher 看到自己从没写过的文本，B 重载并把它自己的想法推回去，**两个窗口轮流 Ctrl+Z 永远不收敛**（而在文档内部看，两边都完全正常）。管这件事的是 **`FDreamUIDocumentRegistry`**（键是**规范化后的绝对路径**），注册表自己的引用是**弱的**；用户持强引用 —— **`FDreamUIDocumentHandle`**，一个**只移动、不可复制**的作用域句柄。
